# 来往账 — 产品规划设计书

**微信小程序 / Product Requirements & Design Specification**  
**v2.0 · 2026-09-12 · R9 语义澄清**

> 产品对外名称尚未最终确定；仓库名暂继续使用 `FamilyLedger`。本文件自 v2.0 起取代 `家庭借款账本_产品规划设计书_v1.1.md`，成为产品、权限、金额语义与开发取舍的权威基线。v1.1 保留为历史文档，不再指导新开发。

## 1. 文档目的与版本变化

v1.1 面向单一家庭场景：曾骏作为固定借款人/管理员，父母和姐姐作为固定出借人。v2.0 将产品重新定义为面向任意微信用户的**双边来往账记录工具**。

核心变化：

- 不再存在固定管理员、固定家庭或全局 `BORROWER/LENDER` 角色。
- 每个微信用户拥有自己的独立账户。
- 同一个用户可以在不同借款关系中分别作为借款人或出借人。
- 一笔借款只有一份共享账本，双方从不同方向查看同一份事实，不维护两份需要同步的副本。
- 任何影响双方正式账本的操作，都必须体现双方同意；发起动作代表发起方已同意，另一方确认后才可正式生效。
- 微信分享只作为邀请/提醒渠道，不承担资金转移，也不作为账本事实来源。
- 继续保留 append-only 事件账本、服务器权威、幂等、审计、整数分和统一计算引擎等既有技术原则。
- v2 采用 **clean rewrite**：旧版只作为 Git 历史参考，不建立长期兼容层、双写层或家庭/管理员兼容分支。

R9 进一步明确：

- `PRINCIPAL_REPAY` 只代表本金减少，不偷偷改成“总付款”；
- `CORRECTION` 是追加补偿事件，不修改历史；
- `CLOSE_LOAN` 是双方确认的最终结清边界，可结清/免除系统未观察到的剩余应计利息，但不得伪造一笔现金支付。

## 2. 产品定位

来往账是一个**双方确认的私人借款记录与对账工具**。

它解决的问题是：熟人之间已经在线下通过微信、银行、现金等方式完成资金往来后，如何让双方用同一份记录确认“谁欠谁、欠多少、利率是什么、发生过哪些还款或调整”。

产品负责：

- 发起借款/借出记录；
- 邀请另一方进入并确认；
- 维护双方共享且可追溯的正式账本；
- 记录还款、追加本金、利率调整、更正等双方确认事件；
- 根据正式事件计算当前本金、利息和应还金额；
- 让每个用户分别看到“别人欠我的”和“我欠别人的”整体状况。

产品不负责：

- 实际转账、收款、提现或资金托管；
- 撮合陌生人借贷；
- 放贷、授信、信用评分、催收；
- 投资理财或收益承诺；
- 证明线下资金一定真实发生；系统记录的是双方共同确认的账务事实。

## 3. 产品核心原则

### 3.1 每个人都是普通 User

`User` 只代表微信身份与产品账户，不携带全局“借款人/出借人”角色。

角色只存在于具体借款关系中：

- 在 Loan A 中，用户可能是 lender；
- 在 Loan B 中，同一用户可以是 borrower。

### 3.2 一笔借款只存在一份共享账本

双方看到的不是两份复制数据，而是同一个 `Loan` 和同一组 `LoanEvent`。

例如 A 借给 B 10,000 元：

- A 首页显示在“别人欠我的”；
- B 首页显示在“我欠别人的”；
- 两边查询到的是同一个 Loan。

任何实现不得通过“给 A 写一份、再给 B 写一份”的方式维护余额。

### 3.3 Shared ledger → shared consent

只要一个操作会改变双方共同认可的正式账本，就必须有双方同意。

发起请求本身代表发起方已同意；另一方接受后，才允许生成正式事件。拒绝、取消或过期都不得影响正式余额。

这条规则取代 v1.1 的“按债务方向决定是否需要确认”。

### 3.4 正式历史追加，不覆盖

`loan_events` 是正式账本历史，已生效事件不得 UPDATE/DELETE。

录入错误通过新的更正/冲正请求解决；更正也需要双方确认，并产生新的正式事件。

### 3.5 余额是计算结果，不是事实源

当前本金、当前利息、当前应还金额必须从：

- Loan 静态关系；
- 已生效 LoanEvent；
- 利率条款；
- 日期规则；

推导得到。

缓存只能作为性能优化，必须可以从正式事件完全重建。

### 3.6 关闭是结清边界，不是付款证明

`CLOSE_LOAN` 表示双方共同确认：截至约定关闭日，该 Loan 已经全部处理完毕，之后不再存在应付余额。

系统可以记录关闭前计算出的剩余应计利息作为审计快照，但不能因为 Loan 被关闭就声称这笔利息一定通过某个支付渠道实际转账。它可能已在线下支付、被免除、取整或通过其他方式处理。

## 4. 核心概念

### User

一个通过微信 OPENID 识别的产品账户。

### Loan

两个 User 之间的一条具体债务关系，明确 `lenderUserId` 与 `borrowerUserId`。同一对用户可以有多笔 Loan，也可以存在方向相反的 Loan。

### LedgerRequest

尚未成为正式账本事实的提议，例如：

- 新建借款；
- 追加本金；
- 还款；
- 修改利率；
- 更正历史；
- 关闭借款。

### LoanEvent

双方已经确认、正式写入且不可修改的账本事件。

### Invite

当对方尚不是系统中已知的交易对象时，用于通过微信分享把某个 LedgerRequest 带给对方的一次性邀请凭据。

## 5. 用户首次进入

未通过邀请进入的新用户首次打开小程序时：

- 服务端根据 OPENID 自动建立/取得 User；
- 首页中“别人欠我的”为 0；
- “我欠别人的”为 0；
- “待我确认”为 0；
- 用户可以立即发起第一笔借款记录。

不再存在 `bootstrapAdmin`、家庭初始化或“第一个用户抢占管理员”的流程。

## 6. 首页信息架构

首页第一屏优先展示三类信息：

### 别人欠我的

汇总当前用户作为 lender 的所有有效 Loan：

- 当前本金合计；
- 当前应还合计；
- 可进入逐个借款人/Loan 查看。

### 我欠别人的

汇总当前用户作为 borrower 的所有有效 Loan：

- 当前本金合计；
- 当前应还合计；
- 可进入逐个出借人/Loan 查看。

### 待我确认

展示所有需要当前用户处理的 LedgerRequest，例如：

- 某人邀请你确认一笔借款；
- 对方记录“已还款 2,000 元”；
- 对方提议修改利率；
- 对方提议更正一笔错误记录。

首页不得显示与当前用户无关的第三方借款信息。

已关闭 Loan 不进入当前 receivable/payable 活跃余额汇总，但仍可从历史入口查看。

## 7. 新建借款流程

用户可以从两个自然方向发起：

- “我借给别人”；
- “我向别人借”。

发起时填写：

- 方向；
- 金额；
- 利率；
- 可选备注；
- 其他当前版本明确支持的条款。

发起后创建 `LedgerRequest(type=CREATE_LOAN)`，但此时不得直接写入正式 LoanEvent。

### 7.1 对方尚未建立系统关系

系统生成一次性 Invite，并让发起人通过微信原生分享能力把小程序卡片发送给对方。

系统不得假设小程序能够读取用户完整微信好友列表，也不得依赖非官方好友读取/自动私信能力。产品流程以“用户主动分享”为基线。

对方打开邀请：

1. 微信身份无感登录/建立 User；
2. 查看借款方向、金额、利率、发起人等信息；
3. 接受或拒绝。

由于首次邀请在创建时通常还不知道对方的真实 OPENID，为降低分享错人/被转发的风险，v2.0 基线采用**首次关系二次确认**：

- 对方接受后，请求进入 `PENDING_INITIATOR_VERIFY`；
- 发起人看到“某用户已接受该邀请”；
- 发起人点击“确认这就是我邀请的人”；
- 系统才原子创建 Loan 并写入初始正式事件。

如果后续产品验证认为该额外一步显著影响转化，可在安全评估后调整，但不能在代码中静默删除。

### 7.2 双方已经有过有效来往

系统可以直接选择“最近往来人/已有交易对象”。此时 `counterpartyUserId` 已确定，不需要 bearer invite 来绑定身份。

发起方提交请求后：

- 对方账户立即出现“待我确认”；
- 发起方可额外通过微信分享该请求作为提醒；
- 对方接受后可直接生效，无需首次关系二次确认。

## 8. 创建 Loan 的正式生效

`CREATE_LOAN` 成功应用时必须在同一事务中完成：

1. 将请求从待处理状态转为 `APPLIED`；
2. 创建唯一 Loan；
3. 写入初始 `PRINCIPAL_ADD` LoanEvent；
4. 写入初始 `RATE_CHANGE` LoanEvent（即使利率为 0，也应明确记录）；
5. 消费 Invite（若有）；
6. 写入必要审计信息。

任何一步失败，整体不得形成“请求已确认但没有 Loan”或“Loan 已创建但请求仍待确认”的半状态。

## 9. 还款流程

还款不要求只能由借款人发起。

借款人可以发起：

> 我已向对方归还本金 ¥2,000

出借人也可以发起：

> 对方已向我归还本金 ¥2,000

二者都创建：

`LedgerRequest(type=PRINCIPAL_REPAY)`。

另一方接受后，事务性完成：

- 请求 `PENDING → APPLIED`；
- 新增正式 `PRINCIPAL_REPAY` 事件；
- 双方下一次读取同一 Loan 时得到相同的新本金与余额投影。

另一方拒绝则请求进入 `REJECTED`，不产生 LoanEvent。

`PRINCIPAL_REPAY` 的业务含义明确限定为**本金减少**，不是一个会自动分配到利息/本金的通用“现金付款”事件。

还款金额不得使本金进入不允许的负值状态；服务器在最终应用事务中重新检查完整事件流和当前本金，不能只信任发起时的客户端计算。

## 10. 追加本金

任意一方都可以发起“追加借款/追加本金”请求。

另一方确认后才产生 `PRINCIPAL_ADD` 事件。

v1.1 中“增加债务可由管理员单方面立即生效”的规则自 v2.0 起废止。

## 11. 利率与 CPI 默认值

利率不是本轮重构的高优先级功能，但 v2.0 数据模型必须避免再次把 5% 写死为业务规则。

产品意图：

- 创建借款时默认利率来源为“当年 CPI 参考值”；
- 用户可以手动修改；
- 最终双方确认的是一个明确的数值利率，而不是一个会在后台静默变化的动态引用。

因此每次正式利率条款必须至少记录：

- `annualEffectiveRate`：双方确认时的明确数值；
- `rateSource`：例如 `CPI_REFERENCE` / `MANUAL`；
- `rateReferenceYear`：若来自 CPI，可记录参考年份；
- 可选 `rateReferenceLabel` / source metadata，用于未来解释来源。

自动获取哪个国家/地区的 CPI、数据源、年度更新时间和跨年自动调整规则暂不在 v2.0 MVP 中定死。

重要原则：**既有 Loan 的利率不得因为外部 CPI 数据后来更新而静默改变。**任何后续利率变化都必须创建 `RATE_CHANGE` 请求并由双方确认。

现有计算引擎的“年化有效利率 + 按日累计/复利”语义继续作为 v2 基线；CPI 只是默认取值来源，不改变计算公式。

## 12. 利率调整

任意一方可以发起 `RATE_CHANGE`。

另一方接受后新增正式 `RATE_CHANGE` LoanEvent，从约定生效日期起参与计算。

任何利率升高或降低都必须确认，不再按“对谁有利”绕过确认。

如果多个已确认利率事件具有同一个 `effectiveDate`，正式事件 `sequence` 更大的后确认事件优先；计算和展示必须使用同一规则。

## 13. 更正与冲正

正式 LoanEvent 不允许直接编辑或删除。更正采用**追加补偿事件**，原事件永久保留。

MVP 的 `CORRECTION` 必须一次只更正一个维度：

- **本金更正**：对一个本金相关事件追加一个有符号的 `principalDeltaFen` 补偿；
- **利率更正**：对一个利率相关事件追加一个 replacement `RateSnapshot`。

不得在同一个 Correction 中同时修改本金与利率。

### 13.1 更正的目标与生效日期

- 本金更正可以引用 `PRINCIPAL_ADD`、`PRINCIPAL_REPAY` 或更早的本金型 `CORRECTION`；
- 利率更正可以引用 `RATE_CHANGE` 或更早的利率型 `CORRECTION`；
- 不允许用 Correction 更改 `LOAN_CLOSED`；
- target event 必须属于同一个 Loan；
- Correction 的正式 `effectiveDate` 由服务端直接继承 target event 的 `effectiveDate`，客户端不能另外指定一个无关日期；
- MVP 不支持“修改历史事件日期”。若只是今天新增/减少本金或从新日期改利率，应使用正常的 `PRINCIPAL_ADD` / `PRINCIPAL_REPAY` / `RATE_CHANGE`。

利率更正还必须引用该 effectiveDate 上**当前实际生效的最后一个 rate-affecting event**，避免选择一个已经被后续同日利率覆盖的旧事件后再次意外覆盖新协议。

### 13.2 本金更正安全规则

本金补偿可以为正或负，但必须是非零安全整数 Fen。

最终接受时，服务器必须在同一事务快照中重放完整本金时间线，并验证从更正生效日起所有账本日边界都不会出现负本金。不能只检查“今天最终本金仍然为正”。

### 13.3 更正流程

1. 任意一方发起 `CORRECTION` 请求并引用 target event；
2. 服务端验证更正类型与 target 类型匹配；
3. 另一方接受；
4. 系统新增一个确定性的 `CORRECTION` LoanEvent；
5. 原事件不改、不删；
6. UI 在历史中同时显示原记录、更正记录及引用关系。

一个 Correction request 在 MVP 中只产生一个 formal Correction event。

## 14. 关闭借款

`CLOSE_LOAN` 是双方确认的**最终结清边界**。

任意一方都可发起关闭请求；另一方确认时必须满足：

- Loan 仍为 ACTIVE；
- 关闭日不得晚于服务器账本“今天”（MVP 不做未来日期关闭）；
- 关闭日不得早于任何已经正式生效事件的 `effectiveDate`；
- 关闭日的当前本金必须严格等于 0；
- 关闭日剩余应计利息不得为负数。

如果本金还未归零，应先通过正常 `PRINCIPAL_REPAY` 完成本金记录。

### 14.1 剩余利息的含义

由于本产品不处理真实资金转移，而 `PRINCIPAL_REPAY` 又明确只改变本金，因此关闭时可能仍存在系统计算出的累计利息。

另一方接受 `CLOSE_LOAN` 即表示双方共同确认：

> 截至关闭日，本金已全部归零；系统计算出的剩余应计利息已经在线下结清、被免除、被双方取整或通过其他方式处理，双方确认该 Loan 此后不再有任何应付余额。

系统必须保存“关闭前剩余应计利息”的服务器计算快照用于审计和展示，但不得把这个快照描述成由本应用完成的一笔付款。

### 14.2 关闭后的余额

关闭不删除或改写任何历史事件。

- 关闭日前的历史 as-of 查询仍按完整事件流正常计算；
- 从关闭 effectiveDate 起，该 Loan 的**当前结清投影**为本金 0、利息 0、总应还 0、今日利息 0；
- 关闭后不再继续累计利息；
- 已关闭 Loan 不进入活跃首页合计；
- Loan 详情仍可展示完整历史以及“关闭时累计利息快照”。

关闭请求的应用必须原子完成：追加 `LOAN_CLOSED`、将 Loan 标为 CLOSED、记录关闭时间、将 Request 标为 APPLIED。

Loan 关闭后，其他尚未应用的本金/利率/更正请求即使此前处于 PENDING，也不得再生效。

## 15. 生效日期与账本时区

所有影响计算的正式事件必须有明确 `effectiveDate`，格式为 `YYYY-MM-DD`。

v2.0 初期继续使用固定账本时区 `Asia/Shanghai`，避免同一 Loan 因设备时区变化而漂移。后续若产品扩展到多地区，可将 `ledgerTimezone` 固化到 Loan；不得在同一 Loan 生命周期中随设备时区漂移。

原则：

- 请求创建时间使用 UTC server timestamp；
- 账务生效使用明确 calendar date；
- 最终生效日期必须由服务器按规则确定或校验，不能完全信任客户端；
- Correction 的 effectiveDate 由 target event 派生；
- MVP CLOSE_LOAN 不允许未来关闭日期，且不得把关闭边界放在已经存在的正式事件之前。

## 16. 金额与计算精度

- 资金金额统一保存为整数“分”（Fen）；
- 业务金额必须是 `Number.isSafeInteger` 范围内的整数；
- 禁止用二进制浮点直接进行金额/利率累计；
- 利息和余额计算统一由 `packages/calc` 提供；
- 前端、云函数、测试不得各自维护一套公式；
- 日利息不是 LoanEvent，不每天写流水；
- 同一 effectiveDate 的利率冲突必须用正式 event sequence 确定顺序；
- CLOSED Loan 的当前结清投影从关闭日起固定为 0，但关闭前历史数学结果仍可重放。

## 17. Request 状态模型

v2.0 基线状态：

- `PENDING`：等待另一方接受；
- `PENDING_INITIATOR_VERIFY`：首次未知对手方已接受，等待发起人确认身份；
- `APPLIED`：已正式应用到账本；
- `REJECTED`：另一方拒绝；
- `CANCELLED`：发起方在生效前撤销；
- `EXPIRED`：邀请/请求超过有效期。

核心状态约束：

- 只有待处理状态可以进入终态；
- `APPLIED` 必须与正式账本写入保持事务一致；
- 已 `APPLIED` 的请求不得回退；
- 已拒绝/取消/过期请求不得生成正式事件；
- 重试必须幂等。

## 18. 身份、权限与隐私

### 身份

- 微信 OPENID 只能由可信云端运行时取得；
- 客户端不得提交一个 OPENID 来声明“我是这个用户”；
- `users.openid` 必须唯一。

### Loan 可见性

只有：

- `loan.lenderUserId`；
- `loan.borrowerUserId`

可以查看该 Loan 的详细账本。

### Request 可见性

只有请求参与双方可以查看完整内容；首次邀请未绑定对方 OPENID 时，持有有效 invite token 的用户只能查看完成接受所必需的最小信息。

### 写权限

客户端不得直接写正式业务集合。所有创建请求、确认、拒绝、取消、应用事件等操作必须经过云函数服务端校验。

## 19. 邀请安全

Invite 必须：

- 使用高熵随机 token；
- 数据库只保存 token hash；
- 原始 token 仅用于分享路径；
- 有过期时间；
- 支持撤销；
- 首次成功 claim 后不得被另一 OPENID 再次 claim；
- token 的 claim、请求状态变化及最终 Loan 创建必须避免半状态。

默认邀请有效期可继续采用 7 天，未来可配置。

## 20. 幂等、并发与事务

这是资金记录系统，不允许“多数时候正确”。

必须满足：

- 所有写请求带客户端生成的 idempotency key；
- 同一 idempotency key 的重试只能返回原结果；
- 若同一 key 被复用于不同 payload，服务端必须返回冲突，不得把旧结果伪装成新请求成功；
- Request 终态转换使用 CAS/事务，不能靠“先查再写”；
- 创建 Loan、应用 Request、生成 LoanEvent、消费 Invite 等跨文档操作需要原子事务；
- 数据读取必须正确处理 CloudBase 分页，不能默认 `.get()` 返回完整历史；
- 正式事件顺序必须稳定，计算不得依赖数据库未定义返回顺序；
- 任何依赖余额正确性的最终确认（如还款、更正、关闭）必须在应用事务内重新读取/重放所需事件，而不是信任 proposal-time 快照。

## 21. 审计与不可篡改层级

v2.0 MVP 的“不可篡改”含义是**业务接口不可修改正式历史**：

- LoanEvent append-only；
- 正常产品流程没有 update/delete LoanEvent 的 API；
- 更正通过新事件；
- 关键写操作有 audit log。

这并不等同于区块链级别的密码学不可篡改：拥有数据库后台管理权限的人理论上仍可直接修改数据库。

若未来产品面向更高信任要求，可增加：

- 事件 canonical hash；
- `previousEventHash` 链；
- 周期性签名快照；
- 外部时间戳/锚定。

这些属于后续安全增强，不阻塞 v2.0 MVP。

## 24. v2 Clean Rewrite 原则

### 可复用的技术资产

- `packages/calc` 单一金额计算源；
- Fen 整数金额；
- Decimal 高精度计算；
- append-only LoanEvent；
- OPENID 服务端身份；
- idempotency key / requestFingerprint；
- AuditLog；
- Repo / MemoryRepo / CloudBaseRepo 分层；
- invite token 只存 hash 的安全原则；
- 通用构建、部署、错误封装与日期工具。

### 明确废弃

- `User.role = BORROWER | LENDER`；
- `familyId`；
- `DEFAULT_FAMILY_ID`；
- 固定曾骏管理员；
- `bootstrapAdmin`；
- 家庭成员全局共享视图；
- admin-only 写入模型；
- direction-based confirmation；
- “新增本金/改利率可单方直接写正式事件”；
- 5% 作为固定产品业务默认值；
- `loan_accounts` / `loan_terms` / `change_requests` 作为 v2 业务模型。

### 不做兼容迁移

v1.1 是开发阶段 PoC，不为其建立长期兼容 API、dual-write 或旧数据迁移框架。若 CloudBase 中仅有测试数据，直接建立/使用 v2 collections；Git 历史就是旧版归档。

只有在以后确认存在值得保留的真实旧数据时，才单独设计一次性导入工具；不得把 v1.1 单方管理员事件静默解释成 v2 的双方共同确认历史。

## 26. v2.0 验收标准

至少满足：

1. 一个全新微信用户无需邀请即可进入空首页；
2. 用户 A 可发起“A 借给 B”或“A 向 B 借”的邀请；
3. 用户 B 打开邀请后以自己的 OPENID 登录并看到正确提议；
4. 首次关系经过接受 + 发起人身份复核后，系统只创建一份 Loan；
5. A/B 从各自账户看到同一 Loan 的相反方向；
6. 任意一方可发起本金还款，另一方接受后双方余额体现同一正式事件；
7. 任意一方可发起追加本金或改利率，另一方确认后才生效；
8. 拒绝/取消/过期请求不改变正式余额；
9. 任意正式本金/利率变化都不存在单方绕过确认的正常 API；
10. 重复点击/网络重试不会产生重复 Loan 或重复 LoanEvent；
11. 并发确认只允许符合最新事务状态的结果生效；并发还款不得把本金变成负值；
12. 超过 CloudBase 单次默认读取数量后，账本仍能读取完整历史并计算正确；
13. 历史正式事件不能通过产品 API 编辑或删除；Correction 只能追加补偿；
14. Correction target 必须属于当前 Loan，且本金更正不能制造任何历史日的负本金；
15. 同日多个正式利率变更按 event sequence 确定最终利率；
16. CLOSE_LOAN 只有在本金为 0 时才能最终接受；关闭事件保存剩余应计利息结清快照；
17. CLOSED Loan 从关闭日起当前应还为 0、不继续计息，但关闭前历史仍可重放；
18. 用户无法读取与自己无关的 Loan/Request/Event；
19. 计算模块对同一事件流始终得到确定、可测试的相同金额。

## 27. Definition of Done

任何涉及以下内容的代码变更，都必须同时更新规格/测试：

- 金额计算；
- 利率语义；
- Request 状态机；
- 身份或权限；
- Loan/Event 的正式事实语义；
- Invite 绑定安全；
- Correction/Close 结清规则；
- 数据库索引/事务要求。

一个功能只有在以下条件同时满足时才算完成：

- 产品语义明确；
- 服务端权限校验存在；
- 幂等与并发路径被测试；
- MemoryRepo 单元测试通过；
- CloudBase 实现与接口语义一致；
- 关键真实链路在两个微信身份上完成集成回归。

# 家庭借款账本 — 产品规划设计书

**微信小程序 / Product Requirements & Design Specification**  
**v1.1 · 2026-09-11**

## 1. 文档目的与产品基线

本文件是“家庭借款账本”微信小程序的产品与实现基线。后续需求讨论、UI 设计、数据库设计、测试和开发，应优先遵照本文件；如有变更，应通过版本化文档明确修改，而不是在代码中静默改变规则。

产品本质是家庭成员之间的借款记录与透明查询工具，不是银行账户、存款账户、基金或理财产品，也不负责实际托管资金。界面必须明确区分“借款本金”和“曾骏 当前应还金额”，避免让用户误认为资金仍存放在某个受监管账户中。

## 2. 产品目标

让爸爸、妈妈、姐姐等家庭成员在自愿借款后，可以随时、极其简单地查看自己借给 曾骏 的本金、当前应还金额、累计利息和近期增长。

通过家庭共享视图，让参与者知道“全家一起借给 曾骏”的总体规模，强化透明度；同时保护每个人的详细资金流水。

所有会改变本金、利率或关键条款的操作，都必须经过借款双方确认；账本采用追加式事件记录，不允许管理员偷偷改写历史。

- 老人友好：进入即见核心金额，无用户名、无密码、无复杂导航。
- 透明：金额计算规则清楚，可追溯到每一笔已确认事件。
- 安全：身份由微信账户无感识别；敏感写操作在云端校验。
- 低维护：优先使用微信小程序 + CloudBase Serverless 架构。

## 3. 非目标（V1 不做）

- 不在小程序内收款、转账、提现或托管任何真实资金。
- 不提供投资、理财、收益承诺或金融产品撮合。
- 不做复杂社交、聊天、家庭群功能。
- 不做传统金融 App 式的账号密码、KYC、银行卡体系。
- 不要求每日生成一条利息流水；每日增长为实时计算结果。
- 不默认公开其他家庭成员的逐笔交易流水。

## 4. 用户角色与权限模型

V1 只有两类业务角色：借款人（曾骏 / 管理员）和出借家庭成员（妈妈、爸爸、姐姐等）。同一微信身份只能绑定一个家庭成员账户，管理员拥有全局账本视图。

推荐统一规则：所有已加入同一家庭计划的成员都能看到每位家庭成员的当前本金、累计利息、当前应还金额以及全家合计；只有本人和 曾骏 能看到该成员的逐笔交易、待确认操作和历史明细。

| 信息 | 本人 | 其他家人 | 曾骏 管理员 |
|---|:---:|:---:|:---:|
| 当前应还金额 | ✓ | ✓ | ✓ |
| 借款本金 | ✓ | ✓ | ✓ |
| 累计利息 | ✓ | ✓ | ✓ |
| 全家合计 | ✓ | ✓ | ✓ |
| 逐笔交易流水 | ✓ | ✗ | ✓ |
| 待确认操作 | ✓ | ✗ | ✓ |

## 5. 核心业务规则（已定）

规则 A — 借款性质：系统展示的是 曾骏 对家庭成员的债务，而不是“存在系统里的钱”。核心文案优先使用“曾骏 应还你”，避免单独使用容易误导的“账户余额”。

规则 B — 按方向确认（v1.1 简化）：确认要求取决于操作对债务的方向，核心原则是“谁被这笔操作损害，谁来确认”。

- 增加 曾骏 债务的操作（新增本金 PRINCIPAL_ADD、上调利率 RATE_CHANGE、调高债务的更正），由管理员（曾骏）单独发起、立即生效，无需出借人确认——因为这类操作只对出借人有利、只对借款人不利，不存在借款人损害出借人的风险。
- 减少 曾骏 债务的操作（归还本金 PRINCIPAL_REPAY、调低债务的更正），由管理员发起后，必须经对应出借人确认才生效——因为这类操作对借款人有利、对出借人不利，出借人需要亲自确认“我确实收到了这笔钱 / 同意这次减免”。

说明：本 V1 面向单一家庭、成员彼此高度信任，因此采用上述非对称简化，而非原始的“任何操作双方确认”。已知残留点：下调利率（RATE_CHANGE 调低）在方向上对出借人不利，本版仍允许管理员单独执行，属为极简而接受的取舍；若未来家庭规模扩大或信任前提变化，应回退为对减少债务方向的操作一律要求确认。

规则 C — 不可篡改历史：已生效交易事件不允许编辑或删除。如录入错误，通过新的“冲正/更正事件（CORRECTION）”修复。更正事件遵循规则 B 的方向判断：调高债务的更正管理员可单独执行，调低债务的更正需出借人确认。

规则 D — 利息：V1 基线采用年化有效利率 5.00%，按日累计/复利展示。日利率 r = (1.05)^(1/365) - 1，使连续持有一年时 100,000 元理论上变为 105,000 元（忽略金额四舍五入和中途本金变动）。

规则 E — 计算而非记账：系统不需要每天写入一条利息交易。当前应还金额由已确认事件 + 生效日期 + 利率条款实时计算；只有真实资金变化和条款变化才写入账本。

规则 F — 生效日期（v1.1 明确）：每笔本金变动必须有明确生效日期。

- 新增本金 PRINCIPAL_ADD：生效日期恒为管理员录入当天（管理员在实际收到款项后补录），不支持补录历史日期。若录入晚于实际到账日，出借人只是少计了几天利息，风险方向对出借人无害。
- 归还本金 PRINCIPAL_REPAY：生效日期取出借人确认当天。
- 利率调整 RATE_CHANGE：生效日期为管理员录入当天。

V1 不支持任意补录历史生效日期，以保持极简并避免利息计算歧义。

规则 G — 金额精度：数据库以“分”为整数保存资金金额，计算过程使用高精度十进制；UI 展示到人民币分。

## 6. 家庭共享规则

家庭成员首页包含“我的借款”和“全家借款”两个区域。全家借款区展示家庭成员姓名/称呼、借款本金、当前应还金额，以及全家当前应还总额。

详细流水保持私有：妈妈不能查看爸爸某天具体新增/取回了多少钱；爸爸也不能查看姐姐的逐笔历史。曾骏 作为借款人可查看全部明细。

如未来家庭成员要求更严格隐私，可在 V2 增加个人可见性设置；V1 为了极简，不增加设置页，采用统一家庭共享规则。

## 7. 身份与首次绑定

产品目标是“无密码”，不是“无身份验证”。小程序通过微信身份无感识别用户；在微信云开发链路中，云函数可以取得调用者的 OPENID，用于服务端绑定和授权。

首次管理员引导（v1.1，first-caller-claims）：为解决“邀请由管理员创建、但第一个管理员无人邀请”的先有鸡还是先有蛋问题，部署后由 曾骏 本人在手机上调用一次 `bootstrapAdmin`。第一个调用的微信账户成为借款人/管理员并绑定其 OPENID；此后该操作永久拒绝（再调用返回 CONFLICT），无法被用于事后夺取管理员。存在短暂的“先到先得”窗口，属为极简接受的取舍。

首次加入采用一次性邀请绑定（v1.1，auto-create-on-bind）：曾骏 在“邀请管理”输入家庭成员称呼（妈妈/爸爸/姐姐）→ 云端生成带一次性 token 的邀请，仅保存 token 哈希，原始 token 只返回一次供分享；此时并不创建成员账户 → 家人点击邀请链接 → 页面通过只读 `previewInvite` 显示“这是你的家庭借款账户：妈妈/爸爸/姐姐” → 点击一次“确认是我” → 云端以 compare-and-set 消费该 token（usedAt 从 null 置为当前时间），胜出者才继续，随后自动创建该成员的 LENDER 账户与对应借款关系，并将其微信 OPENID 绑定；token 立即失效。

绑定安全要点：同一微信身份至多绑定一个账户（users.openid 唯一索引），重复绑定返回 ALREADY_BOUND；token 未找到/已用/过期分别返回 INVITE_INVALID/INVITE_USED/INVITE_EXPIRED；单次使用由 token 消费的 compare-and-set 保证，并发第二次点击必败。邀请有效期 7 天。

后续同一微信账号再次打开小程序，直接进入自己的首页，不再出现用户名、密码或登录页。解绑/换微信账户属于高风险管理操作，应仅由管理员发起，并保留审计记录。

## 8. 普通家庭成员 UX

首页必须在 1 屏内完成核心查询。第一视觉焦点是“曾骏 当前应还你”的大号金额；第二层显示本金、累计利息、今日增长、年利率；第三层显示全家借款概览。

普通用户 V1 只需要两个主要页面：首页 + 我的明细。不要底部五 Tab、不要个人中心、不要设置页、不要退出登录。

- 首页：当前应还金额（最大字号）
- 本金 / 累计利息 / 今日增加 / 年利率 5%
- 全家成员概览 + 全家合计
- 有待确认操作时，在首页顶部出现明显但简单的确认卡片
- “查看我的明细”进入交易历史和按月增长信息

## 9. 管理员 UX

曾骏 进入同一小程序后识别为管理员。管理员首页先展示全家总额及家庭成员卡片；点击成员进入其详细账本。

V1 管理操作只保留必要功能：新增本金、归还本金、查看账本、创建/重发邀请、处理账户绑定。复杂配置隐藏在管理员区域，不能出现在老人首页。

## 10. 操作流程（v1.1，按方向区分）

新增本金（无需确认）：曾骏 在实际收到款项后录入“妈妈新增本金 20,000 元” → 云函数校验管理员身份与幂等键 → 直接生成正式 PRINCIPAL_ADD 事件（生效日期为当天）→ 本金与应还金额即时重算。此路径不经过 change_requests，无待确认状态。

归还本金（需出借人确认）：曾骏 发起“归还妈妈本金 30,000 元” → 生成 change_request，状态 PENDING，requiredConfirmer = 妈妈 → 妈妈打开首页看到确认卡 → 妈妈点击“确认收到归还 ¥30,000” → 云函数以 compare-and-set 将 PENDING→APPLIED，并原子生成 PRINCIPAL_REPAY 事件（生效日期为确认当天）→ 应还金额即时重算。系统只记录双方对账结果，不承担真实资金是否已通过银行/现金完成交付的证明责任。

拒绝请求：妈妈点击“不同意”，请求变为 REJECTED，不产生正式账本事件。已拒绝请求保留审计信息。

利率调整（无需确认）：曾骏 录入新的年化有效利率 → 生成 RATE_CHANGE 事件（生效日期为当天）。见规则 B 关于下调利率的残留说明。

过期策略：仅归还本金存在待确认状态。V1 可暂不自动过期；V2 可增加 7/30 天未确认提醒或自动失效。

## 11. 利息计算模型

V1 采用事件分段计算。每当本金或利率发生有效变化，就形成新的计算区间。某一固定本金 P 在 d 天内的理论余额为 P × (1 + r)^d，其中 r = (1.05)^(1/365) - 1。

如果期间新增本金，新本金只从其生效日起参与计息；如果归还本金，被归还部分从归还生效日起停止计息。实现时不要用浮点数直接累计人民币金额，优先使用 Decimal/高精度十进制。

“今日增加”是当前日期与前一自然日相同时间点的应还金额之差；“本月增加”可由月初与当前余额比较得到。若当日有本金新增/归还，UI 应把“本金变动”和“利息增长”分开展示，避免把新增 20,000 元误称为“今日收益”。

## 12. 数据模型（V1 建议）

核心原则：不要把可修改的 balance 作为账本真相来源。账本真相是已确认的事件（event ledger）；余额属于可重建的派生数据。为性能可缓存 snapshot，但缓存可随时从事件重算。

## 13. 建议事件类型与状态机

正式账本事件建议至少包含 PRINCIPAL_ADD、PRINCIPAL_REPAY、RATE_CHANGE、CORRECTION。利息不是每日事件。

变更请求建议状态：PENDING → APPLIED / REJECTED / CANCELLED。APPLIED 必须和正式事件创建处于同一数据库事务或等价的原子逻辑中，防止出现“请求已确认但事件没写入”的中间状态。

## 14. 技术架构

推荐 V1：微信原生小程序 + 腾讯云开发 CloudBase。CloudBase 当前提供数据库、身份认证、云函数、云存储等 Serverless 能力；微信小程序可通过 wx.cloud.callFunction 调用云函数，云函数侧可获得微信用户身份信息。

关键安全边界：前端只负责展示和发起请求，不拥有最终写账权限。正式事件创建、权限校验、双方确认状态检查、利息计算和账户归属验证均放在云函数/服务端执行。

## 15. 数据安全与审计

- 客户端不得直接修改正式账本集合。
- 所有写操作记录 actorOpenId/userId、服务器时间、请求 id 和结果。
- 正式事件不可 UPDATE/DELETE；更正通过追加事件完成。
- 一次性邀请 token 仅保存哈希或不可逆摘要，使用后立即失效，并设置有效期。
- 管理员身份由服务端角色表判断，不能相信前端传入的 role。
- 关键接口实现幂等 idempotency key，避免用户连点造成重复入账。
- 定期备份数据库；至少支持管理员导出 CSV/JSON 账本。
- V1 不收集身份证、银行卡、手机号等非必要信息。

## 16. 数据库集合 / 表（建议）

| 集合 | 用途 | 是否允许普通更新 |
|---|---|---|
| `users` | 微信身份与家庭角色绑定 | 受限 |
| `loan_accounts` | 借款关系元数据 | 受限 |

## 18. V1 验收标准

- 新家庭成员通过一次性邀请完成首次绑定后，再次打开无需输入用户名或密码。
- 普通成员打开首页 3 秒内可看清自己的当前应还金额、本金、累计利息和今日利息增长。
- 所有家庭成员能看到其他成员的当前汇总金额和全家合计，但无法读取其他成员逐笔流水。
- 管理员可以查看所有账户及所有正式事件。
- 任何本金增减在双方确认前不得影响正式余额。
- 重复点击确认、网络重试不得产生重复事件。
- 已生效正式事件不能从正常业务接口编辑或删除。
- 给定同一组事件和日期，前端展示、服务端计算和测试用例必须得到完全一致的金额。
- 跨闰年、跨月、当天新增/归还、多次本金变化等场景有自动化测试。
- 数据库中不存在依赖每日定时写利息才能保持正确余额的设计。

## 19. 开发阶段建议

建议按“规则引擎 → 身份绑定 → 只读首页 → 双确认写账 → 管理员 → 审计/备份 → UI 打磨”的顺序开发。先用测试锁死钱和权限，再做视觉层。

## 20. 后续可选功能（V2+）

- 按月余额/利息折线图。
- 微信订阅消息：有待确认操作时提醒。
- 每月对账摘要 / PDF 或 Excel 导出。
- 家庭成员自主选择“是否向其他家人显示金额”。
- 条款版本化：不同家庭成员可拥有不同利率或不同生效期。
- 共同管理员或紧急联系人。
- 离线缓存最近一次只读余额（明确标注“截至某时间”）。

## 21. 决议与暂不决定的问题

已在 v1.1 决定：

- 新增本金：仅管理员发起，无需出借人确认，生效日期为录入当天（见规则 B、规则 F、§10）。
- 归还本金：按“减少本金”事件（PRINCIPAL_REPAY）处理，不做“利息优先结清”；V1 不引入独立的 INTEREST_PAYMENT。
- 补录历史日期：V1 一律不支持任意补录，简化利息计算（见规则 F）。
- 利率调整：管理员可单独调整（含下调，属接受的残留取舍，见规则 B）。

暂不决定：

- 家庭成员是否全部使用人民币；若未来涉及 AUD/CNY 多币种，必须按独立账户处理，不能把汇率波动混入利息。
- 产品最终运行和借款关系适用哪个司法辖区；正式投入使用前应根据实际所在地确认借款、利息、税务和证据留存要求。

## 22. 产品文案原则

核心文案应该朴素、明确、家庭化。避免使用“理财、收益、存款、账户资金安全、保证收益”等容易让人误解产品性质的金融措辞。推荐：家庭借款、借款本金、曾骏 应还你、累计利息、今日利息增加、全家借款合计。

任何涉及钱的确认按钮必须写明动作和金额，例如“确认新增本金 ¥20,000”，不要只写“确定”。

## 23. Definition of Done（后续实现遵循）

一个需求只有在同时满足业务规则、权限、金额精度、异常重试、自动化测试和老人 UI 可理解性时才算完成。对金额或权限语义有影响的修改，必须同步更新本设计书或后续版本的变更记录。
